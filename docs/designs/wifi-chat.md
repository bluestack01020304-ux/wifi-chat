## Problem Statement
같은 집 또는 같은 회사 Wi-Fi에 접속해 있는 사람끼리만 대화할 수 있는 웹 채팅을 만든다. 모든 참가자는 동등하고, 계정이 없으며, 원하면 익명으로 말할 수 있다. 쓰임새는 두 가지다.
- 가족: 집에 있는 사람끼리만 닿는 메시지("밥 다 됐다"). 접속자 목록은 "지금 이 방을 열어둔 집 안 사람"을 보여준다.
- 회사 회의: 회의실 안 사람만 보는 익명 대화. 메시지가 회사 네트워크 밖으로 나가지 않는다는 보안 약속이 핵심이다.

## What Makes This Cool
- 대화 상대가 "친구 목록"이 아니라 "지금 같은 공간에 있는 사람"으로 정해진다.
- 처음 웹을 연 사람의 브라우저가 그대로 서버(호스트)가 된다. 설치도, 서버를 켜는 사람도 없다.
- 호스트가 떠나도 남은 사람 중 한 명이 이어받는다. 호스트는 특권이 아니라 잠깐 맡은 역할이다.
- 회의 모드에서 메시지는 같은 네트워크 안의 직접 연결로만 오간다. 중계 서버(TURN)를 아예 설정하지 않으므로 외부로 나갈 경로가 없다(배포된 코드가 변조되지 않았다는 전제에서).
- 익명은 "다른 참가자에게" 익명이다. 호스트는 연결 단위로 누가 보냈는지 알 수 있고, 화면에도 그렇게 표시한다.

## Constraints
- 웹(브라우저)만으로 동작해야 한다. 앱 설치 없음.
- 브라우저 탭은 포트를 열 수 없다. 처음 연결에는 자체 중개 서버(signaling)가 반드시 필요하다.
- 브라우저는 자기 공인 IP나 Wi-Fi 이름(SSID)을 알 수 없다. 방 키는 중개 서버가 요청의 출발지 IP로 계산한다.
- 최신 브라우저는 WebRTC 로컬 주소를 mDNS(`xxxx.local`) 이름으로 감춘다. 기기 간 mDNS 해석이 실패하면 같은 Wi-Fi여도 직접 연결이 안 될 수 있다.
- 모바일 브라우저는 탭이 백그라운드로 가거나 화면이 꺼지면 WebRTC 연결을 멈추거나 끊는다.
- 회사 Wi-Fi는 기기 간 격리, 멀티캐스트 차단, VLAN 분리로 직접 연결을 막을 수 있다.
- 취미 프로젝트. 운영 비용은 0에 가깝게 유지한다(Cloudflare 무료 티어).

## Premises
1. 대상은 공공 Wi-Fi가 아니라 집과 회사 내부 Wi-Fi다. 공공 Wi-Fi(지하철, 카페)는 client isolation 때문에 기기 간 통신이 막혀 있어 제외했다. 사용자 결정.
2. 처음 웹을 연 사람의 브라우저가 호스트가 된다. 자체 중개 서버가 방 키별로 누가 호스트인지 정하고 소개만 하며, 메시지는 WebRTC로 같은 네트워크 안에서만 오간다. 사용자가 제안해 채택.
3. 모든 유저는 동등하다. 계정, 관리자가 없다. 닉네임은 자동 생성된다. 방 이름과 모드(가족/회의)는 입장 URL(또는 그 URL을 담은 QR)에 고정되며, 아무도 대화 중에 바꿀 수 없다.
4. 회의 모드는 "메시지 외부 전송 없음 + 방이 비면 삭제"를 약속한다. 중개 서버는 연결 정보만 보고 메시지 내용은 보지 못한다. 호스트는 완전히 신뢰받는 참가자다(아래 신뢰 모델 참고).

## Approaches Considered
### Approach A: 로컬 서버 프로그램
첫 사람이 Node 단일 파일 서버를 실행하고 나머지는 http://192.168.x.x로 접속. Effort S (human ~2일 / CC ~30분), Risk Low. "웹만 열면 된다"는 경험을 놓쳐서 주 방식으로는 채택하지 않음. 단, mDNS나 회사 네트워크 때문에 B가 실패하는 환경의 대비책으로 남겨 둔다.
### Approach B: 브라우저 호스트 + WebRTC (채택)
아래 Recommended Approach 참고. Effort M (human ~1-2주 / CC ~3-4시간), Risk Med.
### Approach C: QR 손님 초대
중개 서버 없이 QR로 연결 정보를 교환. 입장할 때마다 호스트도 참가자 QR을 스캔해야 해서 사용감이 거칠어 채택하지 않음.

## Recommended Approach
**B: 브라우저 호스트 + WebRTC, 자체 중개 서버가 호스트를 정한다.**

### 구성 요소
- **정적 웹 페이지**: GitHub Pages 또는 Cloudflare Pages. 라이브러리는 CDN이 아니라 같은 저장소에서 직접 제공한다(가능하면 SRI 해시 포함).
- **중개 서버(필수)**: Cloudflare Workers + Durable Object 하나당 방 키 하나. 브라우저와 WebSocket으로 연결한다. 공개 PeerJS 브로커는 쓰지 않는다. WebRTC는 브라우저 기본 API(RTCPeerConnection + DataChannel)로 직접 다룬다.

### 방 키
- 방 키 = (출발지 네트워크 식별자, 방 이름, 모드). 브라우저가 계산하지 않고 중개 서버가 요청의 출발지 IP로 계산한다. 그래서 다른 네트워크에서는 같은 방 키에 들어올 수 없다.
- 출발지 네트워크 식별자: IPv4면 그 주소, IPv6면 앞 /64 접두어. 듀얼스택에서 같은 집의 기기가 서로 다른 키를 받지 않도록, 중개 서버 접속 주소는 IPv4 전용 호스트명(A 레코드만)을 쓴다. IPv4가 없는 기기만 /64로 처리한다. Cloudflare에서 IPv4 전용 호스트명이 가능한지 첫 스파이크에서 확인한다(Open Questions).
- 방 이름과 모드는 URL에서 온다. 예: `/?room=3층회의실&mode=meeting`. 파라미터가 없으면 `room=기본`, `mode=family`. 같은 IP 안의 여러 회의실은 방 이름으로 나뉜다.
- 프라이버시: 중개 서버는 IP를 방이 살아 있는 동안 메모리(Durable Object)에만 두고 로그나 저장소에 남기지 않는다. 방 키에 IP 해시를 쓰더라도 IPv4 해시는 쉽게 역산되므로 "익명화"라고 주장하지 않는다.

### 연결 설정 (외부 전송 차단)
- `new RTCPeerConnection({ iceServers: [] })`. STUN도 TURN도 설정하지 않는다. 그러면 생성되는 후보는 host 후보(로컬 주소 또는 mDNS 이름)뿐이다.
- 수신한 ICE 후보 중 `typ host`가 아닌 것은 버린다.
- 연결 직후 `getStats()`로 선택된 후보 쌍의 local/remote 후보 타입이 둘 다 `host`인지 확인하고, 아니면 즉시 연결을 끊는다.
- 직접 연결이 5초 안에 안 되면 "같은 Wi-Fi가 아니거나, 이 네트워크가 기기 간 연결을 막고 있어요" 화면을 보여준다. 이것이 "같은 Wi-Fi" 판별의 최종 증거다.

### 호스트 선출과 그룹
- 중개 서버가 방 키마다 그룹 목록을 가진다. 그룹 = 호스트 1명 + 그 호스트에 직접 연결된 참가자들.
- 새 참가자는 중개 서버를 통해 각 그룹의 호스트에 순서대로 연결을 시도한다(그룹당 5초). 연결된 그룹에 합류한다.
- 어떤 그룹에도 연결되지 않으면 새 그룹을 만들고 그 그룹의 호스트가 된다. 같은 공인 IP를 쓰지만 서로 닿지 않는 사람들(게스트 Wi-Fi, 유선/VLAN 분리, 같은 IP의 통신사 NAT 모바일 사용자)은 각자 다른 그룹이 되어 서로 섞이지 않는다. 한 사람이 방을 막아버리는 일도 생기지 않는다.
- 호스트 ID를 선점하는 개념이 없다. 호스트는 항상 중개 서버가 같은 방 키(같은 출발지 네트워크)에 접속한 사람 중에서 정한다. 그래서 인터넷의 제3자가 방을 점거할 수 없다.
- 가능하면 데스크톱(화면이 꺼지지 않는 기기)을 호스트로 우선한다. 새 그룹에서 데스크톱 참가자가 들어오면 다음 승계 때 우선 후보가 된다.

### 호스트 승계
- 중개 서버가 그룹별 현재 호스트의 유일한 기준이다. 참가자 간 합의가 없으므로 호스트가 둘로 갈리는 일이 없다.
- 호스트는 중개 서버에 1초마다 heartbeat를 보낸다. WebSocket이 닫히거나 heartbeat가 2초간 없으면 중개 서버가 그룹에서 가장 먼저 들어온 남은 참가자(데스크톱 우선)를 새 호스트로 지정하고 그룹 전체에 알린다.
- 나머지 참가자는 중개 서버를 통해 새 호스트와 연결한다. 승계 중에 들어온 신규 참가자는 중개 서버가 알려주는 새 호스트에 연결한다.
- 새 호스트도 연결되지 않으면 다음 후보로 넘어간다. 후보가 없으면 그룹이 사라진다.
- 목표: 호스트 탭을 닫은 뒤 3초 안에 대화 재개(heartbeat 감지 최대 2초 + 재연결 ~1초). 첫 스파이크에서 실측한다.

### 메시지와 기록
- 메시지는 호스트를 거쳐 그룹 내에 별 모양으로 중계된다. 중개 서버는 메시지를 보지 않는다.
- 각 참가자는 최근 메시지 최대 100개를 메모리에만 들고 있다. 서버 저장, 브라우저 저장소 저장 모두 없다. 그룹에 아무도 없으면 대화는 사라진다.

### 신뢰 모델 (익명과 무결성)
- 익명 모드의 익명은 **다른 참가자에게** 익명이다. 호스트는 어떤 연결에서 메시지가 왔는지 볼 수 있으므로 발신자를 알 수 있다. 회의 모드 입장 화면과 방 상단에 "호스트는 보낸 사람을 알 수 있어요"라고 표시한다.
- 호스트는 완전히 신뢰받는 참가자다. 메시지를 빠뜨리거나 고치거나 다른 사람인 척 만들 수 있다. v1은 메시지 서명을 하지 않으며, 이 한계를 이 문서와 회의 모드 안내에 명시한다. 서명 기반 무결성은 범위 밖.

### 접속자 표시 (가족 방)
- 접속자 목록은 "지금 이 방 페이지를 열어둔 사람"이다. 폰이 백그라운드로 가서 연결이 끊긴 사람은 30초 동안 "잠시 자리 비움"으로 남았다가 사라진다.
- 그래서 "지금 집에 누가 있나"를 정확히 알려주는 센서라고 약속하지 않는다. 집에 늘 켜진 노트북이나 태블릿이 있으면 그 기기가 호스트를 맡는 것이 가장 안정적이다.

## Open Questions
- mDNS host 후보만으로 폰↔노트북, 폰↔폰 연결이 대상 브라우저(Android Chrome, iOS Safari, 데스크톱 Chrome)에서 되는가? 안 되면 해당 환경은 Approach A(로컬 서버 프로그램)로 보완한다.
- 회사 Wi-Fi에서 직접 연결이 되는가? 안 되면 회사 장면은 Approach A로 보완한다.
- Cloudflare Workers에서 IPv4 전용 호스트명을 만들 수 있는가? 안 되면 IPv4 전용 호스트에 아주 작은 키 발급 엔드포인트를 따로 둔다.
- 별 모양 중계에서 호스트 폰이 감당하는 인원은 몇 명인가? (목표: 10명)
- 익명 모드에서 장난이나 욕설을 막을 최소한의 수단이 필요한가? (예: 방 투표로 일시 숨김)

## Success Criteria
- 같은 집 Wi-Fi의 폰 2대와 노트북 1대가 웹 주소만 열고 10초 안에 같은 그룹에 들어가 메시지를 주고받는다.
- 다른 네트워크(예: 모바일 데이터)에서 접속한 기기는 그 방에 들어가지 못한다.
- 호스트 탭을 닫으면 3초 안에 다른 참가자가 호스트를 이어받고 대화가 계속된다.
- 모든 연결에서 `getStats()`로 확인한 선택 후보 쌍이 양쪽 모두 `host` 타입이다. `srflx`나 `relay`가 선택된 연결은 0건이다.
- 브라우저 개발자 도구에서 메시지 내용이 중개 서버로 가는 요청이 0건이다.
- 같은 공인 IP지만 서로 닿지 않는 두 기기는 서로 다른 그룹이 되고, 둘 다 채팅을 쓸 수 있다.
- 모든 탭을 닫았다가 다시 열면 이전 대화가 남아 있지 않다.

## Distribution Plan
- 정적 웹 페이지: GitHub Pages 또는 Cloudflare Pages. main 브랜치 push 시 자동 배포(GitHub Actions 기본 Pages 워크플로).
- 중개 서버(필수 구성 요소): Cloudflare Workers + Durable Objects 무료 티어. `wrangler deploy`를 GitHub Actions에 붙여 main push 시 배포.
- 사용자 입장 경로: URL 공유, 또는 방 이름과 모드가 들어간 URL을 QR로 만들어 집·회의실에 붙여 둔다.

## Next Steps
1. **스파이크(코드 버리는 실험)**: 중개 서버 없이 두 탭/두 기기가 SDP를 복사-붙여넣기로 교환하며 `iceServers: []` 설정으로 연결되는지 확인. 폰↔노트북, 폰↔폰, 회사 Wi-Fi에서 각각 시험하고 mDNS 성공 여부를 기록한다.
2. Cloudflare Worker + Durable Object 중개 서버: WebSocket 접속, 출발지 IP 기반 방 키 계산, 그룹 목록, SDP/ICE 중계. IPv4 전용 호스트명 확인.
3. 브라우저 쪽 연결: host 후보만 허용, `getStats()` 검사, 5초 타임아웃과 그룹 순회, 새 그룹 생성.
4. 별 모양 메시지 중계, 접속자 목록, 자동 닉네임, 최근 100개 메모리 기록.
5. heartbeat와 호스트 승계(중개 서버가 지정, 데스크톱 우선), 3초 목표 실측.
